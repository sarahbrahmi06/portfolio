Context and Motivation

Traditional cybersecurity tools are rule-based: they detect known attack patterns but fail against novel or adaptive threats. Meanwhile, enterprise networks are growing in complexity, making manual security monitoring increasingly impractical.

This project addresses both challenges by combining two emerging technologies:

  • Network Digital Twin: A live virtual replica of a network that mirrors its real-time state, enabling safe testing and analysis without touching production.
  • Adversarial Reinforcement Learning: Two AI agents that learn attack and defense strategies autonomously through trial and error, discovering strategies that rule-based systems would miss.

Project Objectives

  1. Build a realistic virtual enterprise network in GNS3 (18 nodes, 3-tier architecture)
  2. Create a digital twin monitoring stack with real-time metrics visualization
  3. Document the network inventory using NetBox with automatic GNS3 synchronization
  4. Conduct manual penetration testing to establish baseline attack results
  5. Establish a real external attack path via ZeroTier routing
  6. Train RL attacker and defender agents that operate on the live network
  7. Compare manual attack results with RL agent performance

Digital Twin, Monitoring Stack

A Network Digital Twin is a live virtual replica of a network that mirrors its real-time state. In this project:

  • GNS3 Network = the "physical" network being twinned
  • NetBox = structural twin (inventory, topology, IP schema)
  • Telegraf + InfluxDB = behavioral twin (live metrics, traffic, CPU)
  • Grafana = visual twin (real-time dashboard)

NetBox, Automatic Network Inventory

NetBox serves as the source of truth for the network inventory. A Python synchronization service polls the GNS3 v3 API every 60 seconds using OAuth2, and creates/updates all devices, interfaces, IP addresses, VLANs, and prefixes automatically.

InfluxDB stores all collected metrics in a time-series format optimized for high-frequency network data. Retention: 30 days. Bucket: network.

Reinforcement Learning Agents

Reinforcement Learning (RL) is a machine learning paradigm where autonomous agents learn optimal strategies through trial and error, receiving numerical rewards or penalties for every action they take within an environment. Unlike supervised learning, RL agents do not require labelled datasets, they learn entirely from the consequences of their own actions.

In this project, two RL agents compete inside a live GNS3 network digital twin in a two-player zero-sum adversarial game:

  • Red Agent (Attacker): Learns to maximise damage to the network by executing a diverse set of 18 cyber-attacks across four strategic phases (reconnaissance, intrusion, lateral movement, impact).
  • Blue Agent (Defender): Learns to minimise damage and maintain network availability using 18 defensive actions spanning immediate response, recovery, and proactive detection.

This adversarial self-play framework forces both agents to continuously adapt their strategies: as the Red agent discovers new attack sequences, the Blue agent must learn to counter them, and vice versa.

Environment Design

The RL environment follows the gymnasium.Env interface and is implemented across seven Python modules:

  • gns3_connector.py : Network Interface (authenticates with GNS3 REST API v3 using JWT Bearer token)
  • state_collector.py : State Observation (queries InfluxDB for real-time SNMP-collected telemetry)
  • attack_executor.py : Attack Simulation Engine (one handler per Red agent attack type, 18 total)
  • defense_executor.py : Defense Simulation Engine (one handler per Blue agent defense type, 18 total)
  • environment.py : Main RL Interface (orchestrates the full simulation)

Action Space

Both agents have 18 discrete actions each. Unlike the traditional approach where Red and Blue simply toggle the same interfaces on and off, our system implements semantically distinct attack and defense types that mirror real-world cybersecurity operations.

Red Agent, 18 Attack Actions

Reconnaissance (Port Scan, Topology Mapping, Traffic Sniffing, Credential Theft), Disruption (Shutdown Link, MAC Flooding, ARP Poisoning, DDoS Simulation, CPU Exhaustion, VLAN Hopping, STP Attack, Shutdown Core Link, DDoS Core Router), and Persistence (Backdoor Creation, Config Tampering, Lateral Movement, Firewall Bypass, VLAN Pivot).

Each attack has two key parameters: Severity (0–1, controls how strongly the attack perturbs the environment) and Stealth (0–1, controls how much the attack raises the anomaly score). High-stealth attacks (e.g., traffic sniffing at 0.85) are nearly invisible; low-stealth attacks (e.g., DDoS at 0.30) cause an immediate spike in the anomaly score.

Blue Agent, 18 Defense Actions

Immediate Response (Port Isolation, MAC Blacklisting, Rate Limiting, ICMP Blocking, Firewall Rule Update, STP Guard Activation, ARP Inspection), Recovery (Restore Link, Traffic Rerouting, VLAN Reassignment, Config Restoration, Failover Activation, Full Network Lockdown), and Proactive (Honeypot Deployment, Anomaly Detection Alert, Dynamic ACL, Traffic Baselining, IDS Alert Response).

Each defense action specifies a counters list,the Red attack names it can neutralise. A defense action only succeeds if at least one of the attacks it counters is currently active. This forces the Blue agent to learn the correct attack-defense mapping rather than randomly applying defenses.

Kill Chain System

Real-world attackers follow a structured attack progression known as the Cyber Kill Chain. Our system implements a four-stage kill chain that the Red agent must learn to execute sequentially:

Stage Phase Actions that Advance this Stage
1ReconnaissancePort Scan, Topology Mapping, Traffic Sniffing, Credential Theft
2IntrusionARP Poisoning, VLAN Hopping, MAC Flooding, STP Attack
3Lateral MovementLateral Movement, VLAN Pivot, Firewall Bypass, CPU Exhaustion
4ImpactShutdown Core Link, DDoS Core Router, Config Tampering, Backdoor Creation, DDoS Simulation

Kill chain completion grants the Red agent a massive +50 reward bonus and immediately terminates the episode. If the Blue agent clears all active attacks before Red reaches Stage 4, Blue receives a chain interruption bonus of +30. This mechanism teaches the Red agent to chain actions strategically (scout first, then intrude, then spread, then strike).

Reward Function

Our system uses a multi-factor reward function. Red rewards range from +5 to +20 per attack type, with a core multiplier (×1.5–2.0) when hitting core infrastructure, impact scaling based on the number of affected interfaces, a stealth bonus when the anomaly score stays low, and a +2 per stage kill chain bonus. Triggering a honeypot carries a −30 penalty.

Blue rewards range from +7 to +15 per defense type, with a full recovery bonus (×2.0) when all interfaces are up and no attacks are active, a response speed bonus (+5 for 1-step, +2.5 for ≤3-step), and a +30 chain interruption bonus. A wasted move (defense used when no matching attack was active) carries a −2 penalty.

Scenario Variety

To prevent both agents from overfitting to a single starting condition, each episode begins with one of five randomly selected scenarios: Normal (clean state), Already Compromised (one random non-core interface already down), High Traffic (pre-loaded 50–85% CPU usage), Partial Defense (honeypot already deployed), and Stealth (near-zero anomaly baseline, Red must use high-stealth actions).

Training Algorithm, Deep Q-Network (DQN)

Both agents use Deep Q-Networks with several enhancements for stable training in adversarial settings.

Neural Network Architecture

dqn-architecture ~
Input (80 neurons)
↓
Hidden 1 (256 neurons) · ReLU
↓
Hidden 2 (128 neurons) · ReLU
↓
Output (18 Q-values)

Weight initialisation: Kaiming Normal (He initialisation). Loss: MSE between predicted Q-values and Bellman targets. Optimiser: Adam with learning rate 10⁻³. Gradient clipping: max norm 1.0.

Key Enhancements

  • Target Network: A frozen copy of the Q-network is used for computing Bellman targets, synchronised every 10 training steps. Prevents oscillation during training.
  • Exploration Strategy: ε-greedy exploration with exponential decay (ε₀ = 1.0, εₘᵢₙ = 0.05, decay rate 0.995).
  • Experience Replay: Red uses a standard circular replay buffer (size 5000, batch 64). Blue uses Prioritised Experience Replay, 60% of each mini-batch is drawn from a "hot" queue of transitions recorded during active attacks (mean anomaly score > 0.30), and 40% from the normal queue. This trains the Blue agent disproportionately on situations where the network is under attack.

Self-Play Training Loop

Training follows an alternating Red-then-Blue self-play loop where both agents interact with the same environment within each episode step. Red acts first each step, then Blue observes the post-attack state and responds, simulating the real-world asymmetry where attackers have the initiative. Both agents train after every step (online learning), not just at episode end.

Logging and Metrics

The training loop produces thesis-ready logging across three outputs:

  • CSV Episode Log: 18 columns per episode including scenario type, rewards, epsilon, losses, win counts, kill chain stage, chain interruption, time-to-detect, time-to-recover, network availability %, false-positive rate, honeypot triggers, and per-action success counts.

Key Technical Challenges Solved

  1. GNS3 v3 API Migration: The GNS3 server runs v3.0.5 with a new /v3/ API prefix and OAuth2 authentication, requiring updates to all automation scripts from the documented v2 API.
  2. Config Persistence: QEMU nodes lost NVRAM on restart, solved by writing startup configs directly to GNS3 project filesystems files.
  3. Network Bridging: Connecting the external Kali attacker required iptables rules on the GNS3 host machine (LIBVIRT_FWI chain) and MASQUERADE on the Alpine firewall.
  4. Static Route Conflicts: Both routers had accumulated conflicting static routes that overrode OSPF learned routes, causing routing loop, identified via show ip route analysis and resolved by removing all redundant statics.
  5. Victim-1 Gateway: Docker container start command had wrong gateway (10.20.20.254 instead of 10.20.20.1), fixed in GNS3 node configuration.
  6. SwitchL32 Port Discovery: Victim-1 was connected to Gi0/3 (not the documented Gi1/0), discovered via CDP neighbor detail and ARP table analysis.

Limitations

  • RL training requires GNS3 to be running, agents cannot train offline.
  • SNMP polling interval (60s) may miss rapid attack bursts.
  • Docker containers require explicit startup commands for IP persistence.
  • RL agents currently operate on interface-level actions only, not real attack tools.
  • ZeroTier connectivity is required for all team members to access the lab.

Future Work

  • Integrate Real-World Tools: Have the Red agent directly call tools like nmap, hydra, and hping3 via the GNS3 API for a more realistic simulation.
  • Add IDS/IPS: Incorporate Snort or Suricata alerts into the Blue agent's observation space to train it using standard security tools.
  • Scale: Add an OPNsense firewall and more complex multi-zone attack scenarios.
  • Faster Detection: Reduce SNMP polling interval to 10s for better attack burst detection.
  • Syslog Streaming: Integrate Syslog streaming from the Alpine firewall for faster event detection.

Conclusion

This project successfully demonstrates that a Network Digital Twin combined with Adversarial RL is a viable and powerful platform for autonomous cybersecurity research. Unlike purely simulated environments like CyberBattleSim, our agents interact with a real virtual network, making the learned strategies more applicable to real-world scenarios.

The manual penetration testing confirmed that the attack surface is properly configured (all 5 attacks succeeded across a real 5-hop network path), and the full monitoring stack (NetBox auto-sync, Telegraf, InfluxDB, Grafana) provides the observability needed for both human analysis and autonomous agent decision-making.

The project overcame significant real-world integration challenges, API version migrations, routing conflicts, config persistence, and network bridging, making it a robust and reproducible platform.
